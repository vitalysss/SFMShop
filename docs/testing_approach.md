# Подход к тестированию SFMShop

## Общая стратегия

В проекте используются модульные тесты и тесты API. Тесты запускаются с помощью pytest, а покрытие измеряется через pytest-cov.

Основные проверяемые области:

- модели;
- утилиты;
- API endpoints;
- валидация входных данных;
- успешные и ошибочные сценарии;
- взаимодействие с внешними зависимостями.

## Структура тестов

```text
tests/
├── __init__.py
├── test_models.py
├── test_utils.py
└── test_api.py
```

## Тестирование моделей

Файл:

```text
tests/test_models.py
```

Проверяются ORM-модели:

- `User`;
- `Product`;
- `Order`;
- `OrderItem`;
- связи между моделями;
- расчёт итоговой суммы заказа.

Также проверяются предметные модели из `src/models`:

- создание пользователя;
- создание и валидация товара;
- запрет отрицательных значений;
- создание и сравнение заказов;
- сериализация;
- корзина;
- стратегии скидок;
- стратегии доставки;
- уведомления;
- способы оплаты;
- фабрика заказов.

Для повторно используемых тестовых данных применяются фикстуры pytest.

## Тестирование утилит

Файл:

```text
tests/test_utils.py
```

Проверяются:

- расчёт скидки;
- расчёт стоимости доставки;
- расчёт итоговой цены;
- поиск товаров в списке и словаре;
- создание каталога товаров;
- проверка возраста;
- проверка email;
- выбор скидки по сумме заказа;
- обработка строк заказов;
- анализ заказов;
- чтение входного файла;
- создание итогового отчёта.

Различные наборы входных данных проверяются с помощью `pytest.mark.parametrize`.

Для тестирования файловых операций используется встроенная фикстура `tmp_path`. Она создаёт отдельную временную директорию для каждого теста.

## Тестирование API

Файл:

```text
tests/test_api.py
```

Проверяются endpoints:

- `POST /api/v1/login`;
- `GET /products`;
- `POST /products`;
- `GET /products/{product_id}`;
- `PUT /products/{product_id}`;
- `DELETE /products/{product_id}`;
- `GET /api/products/{product_id}/full`;
- `GET /api/v1/products`;
- `POST /api/v1/products`;
- `GET /api/v2/products`;
- `POST /orders`;
- `POST /orders/process`;
- `POST /orders/process-background`;
- `GET /api/v1/exchange-rate`;
- `GET /admin`.

Тесты API проверяют:

- успешные ответы;
- коды HTTP;
- структуру JSON;
- фильтрацию и сортировку товаров;
- отсутствие товара;
- неправильный пароль;
- отсутствующего пользователя;
- частично успешную обработку заказов;
- фоновые задачи;
- работу кэша.

## Фикстуры и параметризация

Фикстуры применяются для подготовки:

- пользователей;
- товаров;
- заказов;
- элементов заказа;
- тестовых зависимостей.

Параметризация применяется для проверки:

- скидок;
- стоимости доставки;
- возраста;
- email;
- отрицательных значений;
- различных способов оплаты;
- различных стратегий доставки.

## Моки

Внешние зависимости изолируются через `unittest.mock`.

Используются:

- `patch`;
- `AsyncMock`;
- подмена зависимостей через `app.dependency_overrides`.

Во время тестов не требуются реальные подключения к:

- PostgreSQL;
- Redis;
- MongoDB;
- RabbitMQ;
- внешнему API курсов валют.

Это делает тесты быстрыми и воспроизводимыми.

## TDD

При разработке расчёта доставки использовался цикл TDD:

1. Red — сначала создаётся тест, который не проходит.
2. Green — добавляется минимальная реализация.
3. Refactor — код улучшается при сохранении успешных тестов.

Тот же подход можно применять при добавлении новых моделей, утилит и endpoints.

## Запуск тестов

Запуск всех тестов:

```powershell
python -m pytest tests -v
```

Краткий запуск:

```powershell
python -m pytest tests -q
```

## Проверка покрытия

Покрытие измеряется для областей, указанных в итоговом задании:

- `src.api`;
- `src.models`;
- `src.database.models`;
- `src.utils`.

Команда:

```powershell
python -m pytest tests -q --cov=src.api --cov=src.models --cov=src.database.models --cov=src.utils --cov-report=term-missing --cov-fail-under=81
```

Текущий результат:

```text
78 passed
TOTAL 85%
```

Порог `81%` выбран потому, что по условиям задания покрытие должно быть строго больше 80%.

Из отчёта исключены:

- `src/api/router.py` — старый роутер, который не подключён к приложению;
- `src/api/smoke_tests.py` — ручной диагностический сценарий.

Рабочие API-модули, модели и утилиты остаются в отчёте покрытия.

## Автоматическая проверка

GitHub Actions запускает тесты автоматически при:

- push в `main`;
- push в `develop`;
- pull request в `main`.

Pipeline завершается ошибкой, если тесты не проходят или покрытие опускается ниже 81%.
