# План инфраструктуры SFMShop

## Назначение

SFMShop — backend интернет-магазина на FastAPI. Инфраструктура должна обеспечивать запуск приложения, хранение данных, кэширование, фоновую обработку задач и возможность дальнейшего масштабирования.

## Компоненты системы

В проекте используются следующие компоненты:

- FastAPI — обработка HTTP-запросов;
- PostgreSQL — хранение пользователей, товаров и заказов;
- Redis — кэширование товаров и временных данных;
- MongoDB — хранение логов и аналитических событий;
- RabbitMQ — очередь фоновых задач;
- Docker — сборка приложения;
- Docker Compose — локальный запуск сервисов;
- GitHub Actions — автоматический запуск проверок.

## Локальная инфраструктура

Локальное окружение запускается через `docker/docker-compose.yml`.

В Docker Compose настроены:

- контейнер приложения;
- PostgreSQL;
- Redis;
- постоянные volumes для PostgreSQL и Redis;
- отдельная сеть `sfmshop_network`;
- проверка готовности PostgreSQL.

Схема локального окружения:

```text
Пользователь
     |
     v
FastAPI :8000
   |       |
   v       v
PostgreSQL Redis
```

MongoDB и RabbitMQ могут запускаться отдельно или быть добавлены в Docker Compose при расширении локального окружения.

## План облачной инфраструктуры

Для развёртывания проекта выбран облачный хостинг, например Google Cloud или AWS.

Целевая схема:

```text
Интернет
    |
    v
Load Balancer
    |
    +-------------------+
    |                   |
    v                   v
FastAPI instance 1  FastAPI instance 2
    |                   |
    +---------+---------+
              |
     +--------+--------+
     |        |        |
     v        v        v
PostgreSQL  Redis   RabbitMQ
                       |
                       v
                 Background worker

Логи приложения -> MongoDB
```

## База данных

PostgreSQL является основным хранилищем данных.

На начальном этапе используется один экземпляр PostgreSQL. При росте нагрузки планируется:

- управляемый облачный PostgreSQL;
- резервное копирование;
- автоматическое восстановление;
- read replica для операций чтения;
- мониторинг медленных запросов;
- оптимизация индексов.

Данные PostgreSQL должны храниться в постоянном volume или управляемом облачном хранилище.

## Кэширование

Redis используется для:

- кэширования списка товаров;
- кэширования отдельных товаров;
- временных данных;
- уменьшения нагрузки на PostgreSQL.

При изменении или удалении товара соответствующий кэш инвалидируется.

## Фоновые задачи

RabbitMQ используется для задач, которые не должны задерживать HTTP-ответ:

- обновление остатков;
- создание отчётов;
- отправка уведомлений.

Задачи отправляются из API в очередь и обрабатываются отдельным worker-процессом.

## Масштабирование

Текущая нагрузка оценивается до 100 RPS. Ожидаемая нагрузка составляет 100–500 RPS, пиковая — до 800 RPS.

План масштабирования:

1. Запуск одного экземпляра приложения.
2. Оптимизация запросов и использование Redis.
3. Запуск нескольких экземпляров FastAPI.
4. Распределение запросов через load balancer.
5. Автоматическое масштабирование по CPU, latency и RPS.
6. Использование Kubernetes при значительном росте системы.

Приложение должно оставаться stateless, чтобы любой экземпляр мог обработать запрос пользователя.

## Сеть и безопасность

Для инфраструктуры предусматриваются:

- хранение секретов в переменных окружения;
- запрет добавления `.env` в Git;
- доступ к PostgreSQL, Redis, MongoDB и RabbitMQ только из внутренней сети;
- HTTPS для внешних запросов;
- ограниченные учётные записи для сервисов;
- регулярное обновление Docker-образов;
- резервное копирование базы данных.

## Мониторинг

Необходимо отслеживать:

- количество запросов в секунду;
- время ответа API;
- процент ошибок;
- загрузку CPU и памяти;
- состояние контейнеров;
- количество соединений PostgreSQL;
- попадания и промахи Redis;
- размер очереди RabbitMQ;
- ошибки фоновых задач.

Для сбора метрик можно использовать Prometheus, а для визуализации — Grafana.

## CI

GitHub Actions выполняет:

1. Получение исходного кода.
2. Установку Python и зависимостей.
3. Проверку кода.
4. Запуск тестов.
5. Проверку покрытия выше 80%.

Автоматическое развёртывание пока не подключено. Оно станет отдельным этапом после выбора провайдера и подготовки секретов репозитория.

## Итог

Текущая конфигурация подходит для разработки и учебного запуска. Целевая облачная инфраструктура позволяет постепенно добавлять экземпляры приложения, управляемые базы данных, фоновые workers и автоматическое масштабирование без изменения основной архитектуры SFMShop.
