# Масштабируемая архитектура для SFMShop

## Компоненты
- Load Balancer - нужен для того, чтобы распределять входящий
- трафик между несколькими экземплярами API
- API-серверы - обрабатывают пользовательские запросы. в идеале иметь несколько, чтобы можно было
- распределять нагрузку между ними, что гарантирует отказоустойчивость
- Redis - Кэш перед БД для частых запросов чтения 
- PostgreSQL - основное хранилище данных
- Очередь задач - передаёт долгие и фоновые задачи воркерам, чтобы не ждать их выполнения
- CDN - хранит и отдаёт стиатический контент с ближайшего от пользователя узла

## Масштабирование

- API-серверы — горизонтальное масштабирование, 
- при росте нагрузки добавляем новые экземпляры приложения, а Load Balancer распределяет запросы между ними.

- PostgreSQL — сначала вертикальное масштабирование,
  затем репликация: основной сервер обрабатывает запись,
  read replicas снимают часть нагрузки на чтение.
  При дальнейшем росте можно рассматривать шардирование.

- Redis — используется как общий кэш для всех экземпляров API,
  чтобы уменьшить количество запросов к PostgreSQL.

- Новые ресурсы добавляем при росте нагрузки:
  если RPS на один экземпляр становится слишком высоким,
  CPU долго держится выше 70% или latency p95 растёт выше
  допустимого значения.
## Отказоустойчивость

- Health checks — liveness проверяет жив ли процесс
 readiness проверяет готовность сервиса принимать трафик.
- Резервное копирование — регулярные backup/snapshot Postgre
 и возможность восстановления данных
- Мониторинг — отслеживание RPS, latency, error rate и т.д.
- Отказ одного API-сервера — Load Balancer перестаёт отправлять на него заросы,
 а остальные экземпляры продолжают работать
## Метрики

- RPS — система должна выдерживать 5000+ запросов в секунду.
- Latency p95 — менее 200 мс.
- Latency p99 — менее 1 секунды.
- Availability — не менее 99,9%.
- Error rate — менее 0,1%.
