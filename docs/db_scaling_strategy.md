# Стратегия масштабирования базы данных SFMShop

## Текущая архитектура
PostgreSQL используется для хранения пользователей, товаров, заказов, отзывов
Redis используется для кеша товаров и пользовательских сессий
MongoDB используется для логов
PostgreSQL Primary работает на порте 5432, а Replica работает на 5433
Запись идет в Primary, некритичное чтение в Replica
## Репликация
Представим что у проекта SFMShop много заказов, пользователей и данных
В таком случае проекту понадобится репликация, она поможет снизить нагрузку на основную базу данных
Реплику можно настроить на некритичные запросы которые касаются чтения, 
это поможет разгрузить основную БД
Но у репликации есть проблема - replication lag, это задержка между передачей данных между Primary
и Replica. Из-за этого критичные операции стоит производить только через Primary, такие, как создание заказа
или получение самых актуальных данных в SELECT запросах.
Так же если не настроить fallback и реплика упадёт, запросы к Replica будут завершаться с ошибкой.
Если fallback настроен, это снова будет загружать основную БД
## Распределение чтения и записи
В Replica можно отправить следующие функции:
get_user(user_id)
get_all_users()
get_product(product_id)
get_all_products()
get_reviews_by_product(product_id)
get_reviews_by_user(user_id)
get_user_orders(user_id)
get_user_orders_with_products(user_id)
Они будут использовать get_session(read_only=True) и смогут читать данные из Replica

В Primary можно отправить следующие функции:
create_user(name, email, balance)
create_product(name, price, quantity)
update_product_quantity(product_id, new_quantity)
update_user_balance(user_id, new_balance)
delete_product(product_id)
create_review(product_id, user_id, review_text, rating)
create_order(user_id, product_id)
это функции выполняют INSERT, UPDATE и DELETE, что считается критичными операциями
они используют обычный get_session(), т.к. значение по умолчанию read_only=False
Особый случай это create_order, там довольно много SELECT запросов, но для бизнес-логики
важны самые актуальные данные при создании заказа
## Шардирование
Шардирование понадобится проекту если основная БД перестанет справляться с объемом данных
и количеством операций записи.
В отличие от репликации при шардировании разные части данных хранятся в разных БД, что существенно
снижает нагрузку на Primary
Для SFMShop можно разделить пользователей и заказы между несколькими шардами
## Выбор ключа шардирования
Для таблиц users и orders лучше использовать ключ по user_id, т.к. между ними
происходит большое количество JOIN
Для выбора шарда можно использовать стабильный хеш, он нужен для того, чтобы
один и тот же user_id направлялся в один и тот же шард.
## Компромиссы
Репликация и шардирование помогают масштабировать БД, но усложняют архитектуру проекта
При репликации возникает replication lag, который нужно учитывать в запросах
Если Replica упадёт, а fallback не настроен запросы чтения будут завершаться ошибкой
А если настроен, нагрузку на основную БД увеличится
Шардирование усложняет работу со связанными данными, добавление нового шарда
требует балансировки, что в свою очередь может вызвать проблему переноса данных вручную
Так же при шардировании усложняются транзакции, резервное копирование
## Итоговая стратегия
Оптимизация запросов и индексов
Нужно использовать Redis для кеширования
Если понадобится добавить еще Replica и распределить нагрузку между ними
Шардирование можно использовать только при достижении предела одной Primary
