# Архитектура баз данных SFMShop
В проекте используется гибридная архитектура БД.

PostgreSQL для хранения пользователей, товаров, заказов, отзывов и позиций заказов

Redis используется для кеширования товаров, а так же хранения сессий и временных данных.

MongoDB хранит логи, аналитику и данные с гибкой структурой
## Общая схема
Пользователь
    |
    v
Приложение SFMShop
    --> PostgreSQL - пользователи, заказы, товары
    |
    --> Redis - кеширование товаров и сессии
    |
    --> MongoDB - логи и аналитика
Пользователь отправляет запрос в приложение, приложение обращается к PostgreSQL,
для работы с основными данными. К Redis для быстрого получения кеша и проверки сессий,
а к Mongo Для записи логов и событий
## PostgreSQL
Postgre является основной системой проекта и хранит основные данные.
Она используется для критичных операций, потому что поддерживает 
транзакции, связи между таблицами и внешние ключи.
Запись выполняется в Primary, а некритичное чтение можно отправлять в Read Replica.
## Redis
Redis используется для кеширования списка товаров, отдельных товаров если на них много запросов,
а так же пользовательские сессии.
Кеш уменьшает количество повторных запросов в Postgre, а TTL позволяет удалять их автоматически
по истечению какого-то времени если они не нужны.
Он не является основным источником данных, так как основная информация может быть получена из Postgre.
## MongoDB
MongoDB хранит access и error логи, а так же аналитику и другие документы с гибкой структурой.
Разные типы логов могут содержать разные поля, поэтому Mongo для этой задачи подходит лучше, чем 
реляционная БД
## Сценарий создания заказа
Когда пользователь оформляет заказ, приложение сначала проверяет его сессию через Redis
и определяет, кто выполняет запрос. Потом приложение обращается к Postgre, в одной транзакции
проверяется баланс, остаток товара, создаёт заказ, списывает деньги и уменьшает количество товара.
Если все прошло успешно, приложение удаляет кеш товара в Redis, потому что он устарел, а так же для того,
чтобы пользователь получил актуальное количество при следующем запросе. Затем информация о создании
заказа записывается в MongoDB как лог или аналитическое событие.
Если какая-то из второстепенных БД недоступна, заказ в PostgreSQL не должен отменяться,
потому что это основная бизнес операция и она успешно выполнена
## Минусы гибридной архитектуры
Гибридная архитектура позволяет проекту использовать каждую БД для своей задачи,
но делает проект сложнее.
Нужно все настроить, следить за доступностью, делать резервные копии и обрабатывать ошибки.
Так же мешает несогласованность данных. Второстепенные системы не должны
ломать основную бизнес операцию. А так же такая архитектура требует больше кода, поддержки и инфраструктуры
