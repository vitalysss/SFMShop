# Архитектура SFMShop

SFMShop представляет собой веб-приложение на FastAPI. Основные данные
хранятся в PostgreSQL, Redis используется для кеширования, а MongoDB для
логов. Также приложение умеет обращаться к внешним API, например для
получения курса валют.

Основная схема работы выглядит примерно так:

Client -> Load Balancer -> FastAPI -> Redis / PostgreSQL / External API

Если приложение будет расти и запросов станет больше, можно запустить
несколько экземпляров FastAPI. В таком случае перед ними ставится Load
Balancer, который распределяет входящие запросы между серверами.

Например:

Client
|
v
Load Balancer
|
+--------+--------+
|                 |
v                 v
FastAPI #1     FastAPI #2
|                 |
+--------+--------+
         |
    +----+----+
    |         |
    v         v
 Redis    PostgreSQL

Также FastAPI отдельно может обращаться к MongoDB и различным внешним
сервисам.


## Масштабирование

Для API лучше всего использовать горизонтальное масштабирование. То есть
при росте нагрузки мы не обязательно делаем один сервер всё мощнее, а
можем добавить ещё несколько экземпляров FastAPI.

Например если один сервер уже не справляется с количеством запросов,
добавляем второй, третий и т.д. Load Balancer будет распределять трафик
между ними.

При этом сами API серверы желательно делать stateless. То есть важные
данные пользователя нельзя хранить только в памяти одного сервера, потому
что следующий запрос пользователя может попасть уже на другой экземпляр.

Общие данные поэтому хранятся в PostgreSQL, Redis и других внешних
хранилищах.

PostgreSQL сначала можно масштабировать вертикально, то есть добавить
серверу CPU, RAM и более быстрые диски.

Если нагрузка станет ещё больше, можно добавить реплики для чтения.
Primary будет принимать изменения данных, а read replicas можно
использовать для запросов на чтение.

Шардирование имеет смысл использовать уже при действительно больших
объёмах данных, когда одна база становится узким местом.


## Кеширование

Для часто запрашиваемых данных в проекте используется Redis.

Например список товаров нет смысла каждый раз заново получать из
PostgreSQL, если он запрашивается очень часто.

Схема работы следующая:

1. Приходит запрос.
2. Сначала проверяем Redis.
3. Если данные есть, сразу возвращаем их пользователю.
4. Если данных нет, идём в PostgreSQL.
5. Получаем данные из базы.
6. Сохраняем их в Redis.
7. Возвращаем пользователю.

Это называется подход cache-aside.

Для кеша товаров сейчас используется TTL 3600 секунд, то есть данные
живут в Redis один час.

При изменении или удалении товара старый кеш удаляется. Это нужно чтобы
пользователь не получил устаревшую версию данных.

Также Redis не должен быть критичной частью системы. Если он временно
упал, приложение всё равно должно продолжить работать и просто получать
данные напрямую из PostgreSQL. Ответы будут немного медленее, но сам
сервис не должен полностью перестать работать.


## Балансировка нагрузки

Если FastAPI запущен в нескольких экземплярах, перед ними можно поставить
Load Balancer.

Его задача распределять запросы между серверами.

Можно например использовать Round Robin. В этом случае запросы по очереди
отправляются на разные серверы.

Также можно использовать Least Connections. Тогда новый запрос
отправляется на сервер, у которого сейчас меньше активных соединений.

Load Balancer также должен проверять состояние серверов. Если один
экземпляр FastAPI перестал отвечать, на него временно не нужно отправлять
новые запросы.


## Асинхронность

Так как FastAPI хорошо работает с асинхронным кодом, основные endpoint'ы
в проекте реализованы через async def.

Это особенно важно для операций ввода-вывода, например:

- запросов в PostgreSQL;
- запросов к внешним API;
- работы с Redis;
- одновременного выполнения нескольких независимых запросов.

Для PostgreSQL в части API используется asyncpg, а для внешних HTTP
запросов используется httpx.AsyncClient.

Если несколько запросов не зависят друг от друга, их можно запускать
одновременно через asyncio.gather. Например отдельно получить данные
товара, отзывы и количество просмотров.

В проекте ещё остался старый синхронный ORM-код. Когда его приходится
вызывать из async endpoint, он запускается через asyncio.to_thread, чтобы
не заблокировать event loop.

В дальнейшем такой код можно полностью перевести на асинхронную работу с
БД.


## Внешние API

Приложение также умеет работать со сторонними API.

Например сейчас есть сервис получения курса валют.

Для запросов используется асинхронный httpx клиент.

У внешнего сервиса обязательно должен быть timeout, потому что нельзя
ждать ответ бесконечно. Если внешний API временно недоступен, используется
несколько повторных попыток.

Между попытками используется exponential backoff. Например сначала ждём
1 секунду, потом 2 секунды и после этого пробуем ещё раз.

Если после всех попыток внешний сервис всё равно не отвечает, наше API
возвращает контролируемую ошибку, а не падает целиком.


## Авторизация

Для авторизации используется JWT.

Пользователь отправляет email и пароль на endpoint логина. Пароль
сравнивается с bcrypt-хешем, который хранится в базе данных.

Если данные правильные, сервер создаёт access token.

Внутри токена хранится id пользователя, email и время окончания действия
токена.

После этого пользователь отправляет токен в заголовке:

Authorization: Bearer <token>

Перед выполнением защищённого endpoint FastAPI проверяет JWT через
dependency.

Если токен правильный, запрос выполняется. Если токен неправильный или
истёк, пользователь получает ошибку авторизации.

Важно что JWT сам по себе не шифрует payload. Его основная задача в нашем
случае это подпись данных, чтобы их нельзя было незаметно изменить.


## Валидация данных

Для входящих данных используются модели Pydantic.

Например у товара есть ограничения:

- название должно быть от 2 до 100 символов;
- цена должна быть больше нуля;
- количество товара не может быть отрицательным.

Если пользователь передаст неправильные данные, FastAPI автоматически
вернёт статус 422.

За счёт этого дополнительную ручную проверку большинства простых полей
писать не требуется.


## Фоновые задачи

Для небольших некритичных операций используются BackgroundTasks.

Например после создания товара можно сохранить лог уже после формирования
основного ответа.

Так пользователь не должен ждать выполнения дополнительной операции.

При этом BackgroundTasks не стоит использовать для очень важных или
долгих задач. Если например нужно гарантированно обработать платёж или
отправить большое количество заданий, лучше использовать отдельную
очередь задач и воркеры.


## Отказоустойчивость

Чтобы приложение продолжало работать при различных проблемах, нужно
учитывать несколько сценариев.

Если один FastAPI сервер перестал работать, Load Balancer должен убрать
его из распределения запросов.

Для этого можно использовать health checks.

Liveness показывает, что сам процесс приложения вообще жив.

Readiness показывает, что приложение готово принимать запросы. Например
если критичная база данных недоступна, сервер может быть жив, но ещё не
готов обслуживать пользователей.

Для PostgreSQL также нужны регулярные backup'ы, потому что отказ сервера
не должен приводить к полной потере данных.

Для Redis используется graceful degradation. Если Redis недоступен,
данные просто читаются напрямую из PostgreSQL.

У внешних API используются timeout и retry, чтобы проблемы стороннего
сервиса не зависали внутри нашего приложения.


## Метрики

При высокой нагрузке важно смотреть не только на то, работает приложение
или нет, но и как быстро оно работает.

Основные метрики:

- RPS;
- latency;
- p95 и p99;
- error rate;
- CPU;
- RAM;
- нагрузка PostgreSQL;
- количество Redis HIT и MISS;
- время ответа внешних API.

В качестве ориентиров для системы можно использовать:

RPS: 5000+ запросов в секунду

p95: меньше 200 мс

p99: меньше 1 секунды

Availability: не меньше 99.9%

Error rate: меньше 0.1%

Это не значит что при любом превышении нужно сразу добавлять новый сервер.
Сначала важно понять где именно находится узкое место.

Например если CPU API серверов долго держится выше 70%, можно добавить ещё
один экземпляр.

Если вырос p95, сначала нужно посмотреть что именно стало работать
медленно: база данных, внешний API, Redis или само приложение.


## Производительность

Для ускорения SFMShop используется сразу несколько подходов.

Один из основных это Redis. При повторном запросе товара данные можно
получить из оперативной памяти, а не снова выполнять запрос в PostgreSQL.

Также используется пагинация. Вместо того чтобы возвращать пользователю
сразу все товары, API например отдаёт только первые 10, а остальные можно
получить следующими запросами.

Асинхронность позволяет не блокировать весь сервер пока приложение ждёт
ответ от базы данных или внешнего API.

Для независимых I/O операций можно использовать параллельное выполнение.

Также используется connection pool, чтобы для каждого запроса не создавать
новое подключение к базе с нуля.

В итоге при росте нагрузки основная идея такая: часто используемые данные
стараемся получать из Redis, долгие I/O операции выполняем асинхронно, а
если одного API сервера уже мало, добавляем дополнительные экземпляры и
распределяем запросы через Load Balancer.
