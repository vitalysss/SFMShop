# Выбор баз данных для SFMShop

## PostgreSQL
Это реляционная база данных, она хорошо подходит для проекта потому, что
у нас интернет магазин, нам нужно хранить большое количество связанных данных.
Это удобно, что данные структурированы и мы можем объединять нужные нам данные из связанных таблиц
через JOIN.
Так же очень удобно записывать новые данные и создавать связи между ними
Так же Postgre поддерживает связи через внешние ключи, JOIN запросы и ACID транзакции.
Это важно при создании заказа, списании денег с баланса или проверки остатков товара.
Для этих целей Redis и MongoDB подходят хуже так, как выполняют немного другие функции
и слабо подходят для структурированных данных.
## Redis
Redis хорош тем, что может хранить временные данные и быстро их отдавать,
так же с помощью него можно хранить кеш для более быстрого доступа к списку товаров.
Это помогает уменьшить общее количество запросов к БД. Еще Redis можно использовать для 
хранения сессий и определять авторизацию пользователя по токену. Так же можно для ключей
установить TTL, после которого данные будут автоматически удалены.

## MongoDB
В MongoDB мы храним access и error логи, это удобно потому что они хранятся в формате словаря
и не требуют какой-то жесткой структуры. Благодаря этому мы можем довольно просто записывать
и доставать данные из логов работы магазина.
С помощью Postgre можно добиться такого же результата, но придется создавать много неиспользуемых полей
которые будут засорять БД и никак не ускорят доступ к данным, а только заменят его.
Поэтому Mongo является идеальным вариантом для решения этой задачи.
## Гибридный подход
Гибридный подход означает, что проект использует несколько БД для решения разных задач.
Postgre хранит основные данные о пользователях, заказах, товарах и выполняет критичные операции.
Redis используется для кеширования часто запрашиваемых данных, чтобы разгрузить Postgre и хранит сессии
пользователей. В свою очередь MongoDB хранит логи, аналитику и документы с гибкой структурой.
Так же такой подход можно назвать Polyglot Persistance, мы берем от каждого лучшее, но есть сопутствующие сложности.
При гибридном подходе нужно настраивать и поддерживать сразу 3 системы, а так же обрабатывать ситуации, 
когда одна из второстепенных БД не работает.
## Компромиссы
Polyglot Persistence делает архитектуру более гибкой, но в то же время усложняет поддержку.
Для всех трёх БД треубуется настройка, мониторинг и резервное копирование, а так же обработка ситуаций,
когда одна из БД не работает.
Так же между системами может возникать несогласованность данных, например заказ создан, но лог не записался.
Еще можно отметить, что основная бизнес операция не должна зависеть от второстепенных БД.
Нельзя допускать отмену заказа пользователя, если Redis или MongoDB работают некорректно.
Еще такой подход требует больше кода и контроля, но ускоряет использование сервиса, потому что 
каждый инструмент используется по назначению
