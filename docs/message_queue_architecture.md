# Архитектура асинхронной обработки заказов для проекта SFMShop

## Задачи для очереди

### Отправка email-уведомлений
- Триггер: создание нового заказа   
- Передаваемые данные: order_id, email, статус заказа
- Приоритет: средний

### Обновление склада
- Триггер: Создание или подтверждение заказа
- Передаваемые данные: order_id, список товаров и количество
- Приоритет: высокий

### Генерация отчётов
- Триггер: создание или завершение заказа
- Передаваемые данные: order_id, список товаров, количество, сумма заказа
- Приоритет: низкий


Почему эти задачи выносятся в очередь:
Потому что они не нужны пользователю, чтобы получить ответ от API.
Это позволит быстрее отвечать на запросы о создании заказа не заставляя
пользователя ждать. Так же очередь упрощает повторную обработку задач при
ошибках, а так же позволит масштабировать консьюмеры при росте нагрузки.

---

## Надёжность

### Гарантии доставки
- durable queue
- persistent message
- ACK только после успешной обработки
- если консьюмер упадёт до ACK, сообщение возвращается в очередь

### Retry-логика
- при временной ошибке, обработать сообщение повторно
- количество попыток ограничено
- между попытками сделать задержку

### Обработка ошибок и Dead Letter Queue
- если после всех retry задача падает, сообщение отправляем в DLQ
- DLQ нужен для ручного анализа, исправления причины и повторной обработки

### Идемпотентность Consumer
- Консьюмер должен быть готов к повторной отправке
- для дедупликации использовать уникальный message_id
- message_id которые обработали должны сохраняться
- Если сообщение пришло повторно, не выполнять бизнес-операцию второй раз
- изменение данных и запись message_id делать в одной транзакции
---

## Масштабирование

### Горизонтальное масштабирование Consumer
- если один консьюмер не справляется с нагрузкой, нужно запускать дополнительные
- несколько консьюмеров могут параллельно выполнять задачи в очереди, что увеличит
пропускную способность

### Балансировка нагрузки между воркерами
- Rabbit распределяет сообщения между доступными консьюмерами
- можно использовать prefetch_count=1, чтобы один консьюмер обрабатывал одно сообщение,
- это поможет равномерно распределить задачи

### Мониторинг очередей
- количество сообщений в очереди
- скорость поступления и обработки сообщений
- время обработки задач
- количество retry и ошибок
- количество сообщений DLQ
